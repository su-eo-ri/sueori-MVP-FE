# 수어리 PoC #2 — 채점 알고리즘 (정적: 코사인 유사도 / 동적: DTW)

`수어리 - PRD v1` 5.1의 채점 알고리즘 선택("정적=코사인 유사도, 동적=DTW → 0~100점")이
실제로 말이 되는 동작을 하는지 검증하는 PoC. 카메라/MediaPipe 연동은
`hand_landmark_poc`(이 저장소 밖 `project-sueori/poc/`에 있는 별도 PoC)가 담당하고, 여기서는 그 출력물(21개 랜드마크 / 랜드마크 시퀀스)을
입력받아 점수를 내는 순수 로직만 검증한다. **실제 카메라 데이터가 아닌 합성(synthetic)
테스트 데이터**로 검증했다 — 알고리즘 자체의 동작을 확인하는 단계.

## 실행 방법
앱 저장소(`sueori-MVP-FE`) 루트 기준. 앱은 `pubspec.yaml`에서 `path: packages/scoring_poc`로 이 패키지를 참조한다.
```
cd packages/scoring_poc
flutter test
```
decayFactor 산출용 디버그 스크립트(`bin/`)는 저장소로 옮길 때 포함하지 않았다. 원본은 저장소 밖 `project-sueori/poc/scoring_poc/bin/`에 있다.

## 정규화
21개 랜드마크를 (1) 손목을 원점으로 평행이동, (2) 손목~중지 MCP 거리로 스케일 정규화.
**회전은 의도적으로 정규화하지 않음** — 손바닥 방향이 의미를 구분하는 수어가 많기 때문.

**알려진 한계**: 이 정규화는 프레임마다 손목을 원점으로 되돌리기 때문에 "손 전체가
화면에서 이동하는 궤적" 정보가 사라진다. 손모양은 그대로 유지한 채 위치 이동 자체가
의미를 구성하는 동적 수어가 있다면, 이 부분은 실제 데이터 검증 시 보완이 필요하다
(예: 정규화 전 손목 좌표 변화량을 별도 피처로 추가).

## 발견 1 — 코사인 유사도는 정적 채점에 그대로 쓰기엔 판별력이 부족하다
`CosineScorer`로 "편 손" vs "주먹"(완전히 다른 손모양)을 채점하면 **97점대**가 나온다.
원인: 21개 랜드마크 중 손목+5개 MCP(=63차원 중 18차원)가 두 손모양에서 완전히 동일해서,
손끝이 크게 움직여도 63차원 벡터 전체의 "방향"은 별로 안 바뀐다 — 코사인 유사도가
태생적으로 둔감한 구간.

**대안으로 `DistanceScorer`(정규화된 랜드마크 간 "관절당 평균 유클리드 거리"를 지수
감쇠로 점수화)를 추가 구현·비교**했더니 같은 입력에서 **34점대**로 명확히 구분됨.
→ **정적 채점은 코사인 유사도 대신 거리 기반 방식을 권장.** (`CosineScorer`는 비교
대조군으로 코드에 남겨둠)

## 발견 2 — DTW는 정적 채점과 같은 decayFactor를 그대로 못 쓴다
DTW는 최적 정렬을 찾도록 설계돼 있어서, 완전히 다른 두 동작을 비교해도 프레임 단위
최선의 정렬 비용은 "완전히 다른 한 프레임끼리의 거리"보다 체계적으로 작게 나온다.
정적 채점과 같은 decayFactor(≈2.0)를 그대로 쓰면 **명백히 다른 동작도 80점을 넘겨버려**
채점(전역 통과 기준 80점)이 무의미해짐. → DTW는 별도로 보정한 더 큰 계수(≈6.5)를 사용.

## 발견 3 (긍정적) — DTW는 의도대로 "속도 차이"에 강건하다
같은 "주먹 쥐었다 펴기" 동작을 10프레임 vs 23프레임(느리게 재현)으로 비교하면:
- DTW 점수: **95점대** (거의 동일하게 채점 — 의도한 대로 동작)
- 반면 모양 자체가 다른 동작(펼치기만 하고 다시 안 쥠, 10프레임)과 비교하면 **49점대**

→ "속도만 다름"과 "모양 자체가 다름"을 뚜렷하게 구분한다. 프레임 대 프레임 단순 비교였다면
프레임 수가 다른 두 시퀀스는 애초에 비교조차 할 수 없었을 것 — DTW를 쓰는 이유가
실제로 유효함을 확인.

## decayFactor 값 (PoC 단계 추정치, 실사용 데이터로 재튜닝 필요 — PRD 명시)
| 스코어러 | decayFactor | 근거 |
|---|---|---|
| `DistanceScorer` (정적) | 2.0 | 노이즈(관절당 평균거리 0.057) → 89점 / 완전히 다른 모양(0.539) → 34점 |
| `DtwScorer` (동적) | 6.5 | 같은 모양·다른 속도(평균정렬비용 0.025) → 85점 / 다른 모양(0.111) → 49점 |

## 발견 4 (2026-09-08 추가) — NaN/Infinity 좌표가 섞이면 스코어러가 오히려 만점을 준다
엣지 케이스 테스트(`test/edge_cases_test.dart`) 추가 중 발견: 랜드마크 좌표 하나라도
`NaN`이면 `CosineScorer`/`DistanceScorer` 둘 다 **100점**을 준다(0점이 아니라!).
원인은 Dart의 `num.clamp(lo, hi)`가 값이 `NaN`이면 **upper bound를 그대로 반환**하는
동작 때문 — `similarity`/`distance` 계산이 NaN으로 전파된 뒤 `.clamp(...)`를 거치면서
"가장 좋은 점수"로 둔갑한다. 반면 `Infinity` 좌표는 반대로 0점을 줘서, 같은 "비정상
입력" 범주인데 처리 결과가 정반대로 갈린다(일관성 없음).

**MediaPipe가 손을 놓쳐서 좌표가 비정상적으로 나오는 상황은 실제로 있을 수 있으므로,
프로덕션 이식 시 스코어러에 넘기기 전 입력 검증(모든 좌표가 finite인지)을 반드시
추가해야 한다** — 이 두 스코어러 내부 로직만으로는 안전하지 않음이 테스트로
확인됐다.

## decayFactor 재튜닝 가능 여부 — 솔직한 결론
**이 리포에는 실제 카메라(MediaPipe) 캡처 데이터가 없다.** `hand_landmark_poc`는
"JS interop이 동작하는가"만 검증했고 랜드마크 좌표를 저장/내보내지 않으며, 이
`scoring_poc`의 테스트 데이터는 전부 `test/synthetic_hand.dart`의 손으로 만든 합성
포즈다. 따라서 **지금 시점에 decayFactor를 "실제 데이터로" 재튜닝하는 건 불가능하다**
— `bin/debug_distances.dart`가 이미 하는 것(합성 데이터에서 원하는 점수가 나오도록
역산)보다 더 나은 걸 할 수 없다. 재튜닝하려면 먼저 (1) `hand_landmark_poc`가 실제
랜드마크 좌표를 내보내도록 확장하고, (2) 여러 사람이 여러 단어를 시연한 실제 캡처
데이터를 모아야 한다 — 둘 다 이번 작업 범위 밖.


- 실제 카메라(hand_landmark_poc)에서 뽑은 랜드마크로 재검증 — 합성 데이터는 어디까지나
  "알고리즘이 논리적으로 맞는가"만 확인한 것
- 국립국어원 수어 API 콘텐츠로 실제 "정답 랜드마크" 시퀀스를 뽑아 decayFactor 재튜닝
- 손 궤적(위치 이동) 정보를 놓치는 정규화 한계 — 실 데이터로 필요성 재확인
